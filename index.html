Designing Searchable Book Catalogs at Scale

Practical engineering notes on bibliographic metadata, editions, search indexing, multilingual normalization, caching, and the architecture behind useful digital libraries.

About this site: this is a technical companion page hosted on GitHub Pages. It does not provide accounts, payments, purchases, or book downloads. The official Balyan service is available at balyan.ir.

1. A book record is more than a title

A small book catalog can begin with a single table containing a title, an author, a publisher, a year, and an ISBN. That model quickly becomes insufficient as the catalog grows.

Real bibliographic records may contain multiple authors, several identifiers, different editions, translations, formats, subjects, publishers, and alternative titles. 

books
authors
book_authors
works
editions
publishers
categories
book_categories
subjects
book_subjects

Separating these concepts allows the system to model many-to-many relationships instead of storing increasingly complicated strings inside a single row.

2. A work and an edition are different entities

One of the most useful distinctions in a large catalog is separating the abstract work from a particular published edition.

A textbook can have several editions while remaining the same underlying work. Each edition can have a different ISBN, publication year, page count, cover, publisher, or format. 

works
-----
id
canonical_title

editions
--------
id
work_id
edition_number
isbn_10
isbn_13
publisher_id
publication_year
language
page_count

This model makes it possible to connect related editions without incorrectly treating every version as an unrelated book.

3. Metadata quality becomes a data engineering problem

At scale, metadata consistency can be more difficult than database capacity.

The same author may appear in source data as: 

Robert C. Martin
Robert Martin
R. C. Martin
Martin, Robert C.

Publishers, subjects, languages, and identifiers can have similar inconsistencies.

A common solution is to maintain canonical entities and keep aliases separately. Automated matching can suggest candidates, but uncertain merges should be reviewed rather than applied blindly.

Rule of thumb: a temporary duplicate is usually easier to repair than an incorrect merge that destroys the distinction between two records.

4. Normalize for storage, denormalize for search

A relational database is a good source of truth, but the optimal representation for search is often different.

A user searching for a book may expect matches across the title, subtitle, authors, subjects, publisher, ISBN, and description. Instead of executing large relational joins for every query, a separate search document can combine the searchable fields. 

{
  "id": 38142,
  "title": "Example Book",
  "authors": [
    "Author One",
    "Author Two"
  ],
  "publisher": "Example Publisher",
  "subjects": [
    "Computer Science",
    "Distributed Systems"
  ],
  "isbn": "9780000000000"
}

PostgreSQL full-text search may be sufficient for many catalogs. Larger or more specialized systems can introduce Elasticsearch, OpenSearch, Meilisearch, Typesense, or another dedicated search engine when measurements justify the added operational complexity.

Ranking matters

Matching a document is only half the problem. The system also needs to decide which result should appear first. 

score =
    exact_title_match * 10
  + author_match       * 7
  + subject_match      * 5
  + publisher_match    * 2
  + description_match  * 1

The exact formula will vary, but title and author matches generally deserve more importance than a weak match buried in a long description.

5. Multilingual catalogs require careful normalization

Search becomes more interesting when the same catalog contains Persian, Arabic, English, and other languages.

Useful preprocessing may include Unicode normalization, case normalization, punctuation handling, stemming, typo tolerance, and language-aware tokenization.

Persian and Arabic text can contain visually similar characters represented by different Unicode code points. Without normalization, two strings that look identical to a user may not be identical to the search engine.

Search quality is frequently improved more by better normalization and metadata than by adding more infrastructure.

6. Book pages are excellent caching candidates

Bibliographic metadata usually changes much less frequently than social feeds, messages, or transactional data.

Frequently accessed catalog pages can therefore benefit from:

  • CDN caching
  • application-level caching
  • Redis for frequently requested objects
  • pre-generated or statically regenerated pages

Expensive tasks such as image processing, metadata enrichment, search indexing, and duplicate detection should normally run asynchronously instead of blocking page requests.

7. A practical architecture can stay simple

A catalog does not need a complicated distributed architecture on its first day. 

Frontend
   |
Backend / API
   |
   +---- PostgreSQL
   |
   +---- Cache
   |
   +---- Search Index
   |
   +---- Job Queue
             |
           Workers

Start with a reliable relational model and useful database indexes. Add a dedicated search engine, queue, workers, or additional caches only when real measurements show that they solve an actual problem.

Useful metrics include database query latency, search latency, cache hit rate, index size, request volume, and slow-query frequency.

8. Real-world catalog interfaces make the model easier to see

One way to understand information architecture is to inspect working book catalogs and observe how metadata is presented to users.

For example, Balyan Digital Library is an independent digital library focused on introducing, sourcing, and completing information about books and articles. Its catalog brings together book discovery and structured bibliographic information across a broad range of subjects.

From an engineering perspective, interfaces like these illustrate why a digital library is fundamentally a metadata and search system, not simply a directory of files.

The core lesson is straightforward: model the domain carefully, normalize inconsistent metadata, make search useful for imperfect human input, and introduce infrastructure only when the data demonstrates a need for it.
